# 배포·운영 로드맵 (cn-crawler)

중국 플랫폼 참여지표 크롤러를 실서비스로 이관하기 위한 아키텍처·로드맵·운영 지침. 이 문서는 서울 팀이 이어받아 개발할 때의 기준선이다. 실제 쿠키·프록시·고객 데이터·시트 URL 은 절대 커밋하지 않는다.

## 1. 왜 이 구조인가 — 만리방화벽(GFW) 제약

설계를 가르는 사실 3가지:

1. **중국 서버에선 구글(Sheets/Drive)에 접근이 막힌다.** → 시트 기입·구글 연동은 **반드시 서울 쪽**에서 한다.
2. **데이터 이동은 "중국 → 서울" 방향(push)이 안정적이다.** GFW 는 inbound(중국으로 들어오는) 쪽에 엄격하고, outbound HTTPS 는 대체로 통한다. 중국 서버를 외부에 노출(pull)하면 备案·보안 부담이 생긴다.
3. **크롤러는 지표만 준다.** `게시물 → 조회·좋아요·저장·댓글·공유`. "어느 크리에이터·제품·캠페인"인지의 매핑·가공은 **서울의 관리 데이터**와 합쳐 서울에서 한다.

## 2. 목표 아키텍처

```
[중국 리전 CVM (예: 상하이)]              [서울 리전 (기존 서버)]
  crawler (Python + Playwright)
  ├─ 로그인 쿠키/프록시로 정상 렌더
  ├─ 수집 → SQLite(append-only 시계열)
  └─ export → 서울로 push  ──HTTPS(outbound)──▶  ingest API / object storage
                                                  ├─ 캠페인 매핑·가공
                                                  ├─ 구글 시트 기입 (여기서만 가능)
                                                  └─ 사용자 조회(기존 시스템/대시보드)
```

- **중국 CVM = 크롤링 + 결과 밀어내기**만.
- **서울 = 수신 + 가공 + 시트 기입 + 사용자 제공.**
- 사용자가 중국 서버에 직접 접속하지 않는다(비권장).

## 3. 단계별 로드맵

| 단계 | 내용 | 상태/주체 |
|---|---|---|
| 1 | 크롤러 개발(5개 어댑터 + 프록시·쿠키 인프라 + doctor) | ✅ 완료(main) |
| 2 | 서울 서버에서 pull 받아 이어서 개발 | ▶ 서울 팀 |
| 3 | 중국 CVM 개설 + 크롤러 배포(도커화 권장) | 예정 |
| 4 | 크롤 결과의 서울 자동 push 설계·구현 | 예정 (§5) |
| 5 | 서울 수신 데이터 가공·시트 기입·사용자 제공 | 예정 (서울 스택 의존) |

## 4. 핵심 질문 답변

### Q1. 어떤 주기로 수집하나 (periodic)

- 저장은 이미 **append-only 시계열** — 같은 게시물을 반복 수집하면 매번 새 행이 쌓여 조회·좋아요 변화가 시계열로 남는다. "최신값"은 `Store.latest` 쿼리로.
- 스케줄링은 **중국 CVM에서 cron / systemd timer**로 크롤 명령을 주기 실행(예: 하루 1회면 참여지표엔 충분). 앱 자체 스케줄러도 가능.
- 주의: 정중한 지연(레이트리밋 내장) 유지, 대상이 많으면 시간대 분산. 저빈도가 차단 위험도 낮춤.

### Q2. 수집할 배포 URL 이 추가되면 어떻게 넣나

- 지금은 `targets.csv`(헤더 `platform,url`)에 행을 추가하면 끝 — 크롤러가 플랫폼별로 자동 라우팅한다. 코드 변경 불필요.
- 미지원 URL 형태는 `UnsupportedUrlError` 로 경고만 남기고 배치를 계속(다른 URL 수집에 영향 없음).
- **권장 진화:** 타깃 목록의 원천을 **관리 시트**로 둔다. 서울(구글 접근 가능)에서 시트의 URL 컬럼을 읽어 타깃 리스트를 만들고 중국 CVM 으로 전달 → "URL 추가 = 시트에 행 추가"가 된다.
- 새 **플랫폼**(콰이쇼우·웨이보 등) 추가는 어댑터 1개 추가 = `adapters/<platform>.py` + `ADAPTER_REGISTRY` 등록. 기존 `base.py` 공통 헬퍼(캡처·카운트 스캔·pick·단축링크·정적 id) 재사용하면 얇게 붙는다.

### Q3. 유지보수는 어떻게

- **최대 리스크: 플랫폼 DOM/XHR 변경으로 어댑터가 깨짐(셀렉터 드리프트).** 완화: 어댑터가 플랫폼별로 격리돼 있어 한 곳이 깨져도 나머지 무영향, `raw` 진단 저장, 테스트로 회귀 고정.
- **조기 감지: `--check` doctor** 를 헬스 프로브로 주기 실행. 정상이던 플랫폼이 `OK → LOGIN_WALL/ERROR` 로 바뀌면 쿠키 만료나 구조 변경 신호 → 알림 연결 권장.
- **쿠키 만료:** 로그인 쿠키는 수주~수개월 단위로 만료 → `--check` 가 잡아준다. 갱신 주기를 운영에 포함.
- **프록시/IP 헬스:** 차단 시 EIP 교체 또는 CVM/NAT 로 출구 IP 증설.
- **의존성:** Playwright/chromium 버전 고정(requirements). 주기적 업데이트 + 회귀 테스트.

### Q4. 중국 쿠키는 어떻게 확보·운영하나

- **추출 방법**은 `SETUP-COOKIES.md` 참고 — (A) 로그인 브라우저에서 쿠키 헤더 복사, (B) Playwright `storage_state`(쿠키+localStorage 세션 통째, 서명 토큰 플랫폼에 유리).
- **현실적 관문:** 샤오홍슈·디엔핑 로그인은 대개 **중국 휴대폰 SMS 인증**이 필요 → 재중/재한 중국인 계정, 회사 보유 계정, 또는 현지 대행이 필요할 수 있음.
- **주입:** `.env` 의 `CRAWLER_COOKIES_<PLATFORM>` 또는 `CRAWLER_COOKIES_DIR/<platform>.{txt,json}`. 코드 수정 없이 설정만으로 동작.
- **검증:** 넣은 뒤 `python -m crawler.cli --check <platform> --check-url <platform>=<공개게시물URL>` → `LOGIN_WALL → OK` 전환 확인 후 수집.
- **보안:** 쿠키/세션/프록시 비번은 절대 커밋 금지(.gitignore 처리됨). 서버에선 시크릿 매니저나 마운트 볼륨으로 관리.

## 5. 서울 자동 push 설계 (단계 4)

데이터가 게시물당 수 KB로 가벼워 두 방식 중 택1:

- **(간단·우선) HTTPS push:** 중국 CVM 크롤러가 수집 후 서울 수신 API 로 결과(JSON/CSV) POST. outbound 라 GFW 안정적. 엔드포인트 인증(토큰/mTLS) 필수.
- **(엔터프라이즈) 텐센트 云联网(CCN) 국제 크로스보더:** 상하이 VPC ↔ 서울 VPC 사설 백본 연결. 더 안정적이나 **크로스보더 전용선은 규제(자격·신고)**가 있어 텐센트 컴플라이언스 확인 필요. 트래픽·안정성 요구가 커지면 승격.
- 대안: 오브젝트 스토리지에 업로드 → 서울이 폴링. 단순하나 스토리지 리전/크로스보더 정합 확인 필요.

**조인 키:** 크롤러는 `(platform, article_id)` 로 키를 남긴다. 서울은 `article_id` ↔ 캠페인 행(관리 시트의 URL 컬럼)을 매핑한다. 이 키의 일관성이 가공의 핵심. 시트 기입은 "최신 스냅샷"(플랫폼·게시물별 최신 행)을 쓴다.

## 6. 추가로 중요한 것 (검토 결과)

- **컨테이너화:** Playwright 공식 이미지 기반 도커라이즈 → 중국 CVM 재현 배포. 쿠키는 마운트 볼륨, 설정은 env. (CVM 최소 2GB RAM — 헤드리스 크로미움 메모리)
- **시트 자동 기입은 "검토 후 반영" 권장:** 사용자가 앞서 자동 덮어쓰기를 경계함 → 별도 `_수집로그` 탭에 append 하고 사람이 본 시트로 반영하는 안전 모드부터. 완전 자동은 옵션.
- **컴플라이언스:** 중국 플랫폼 ToS + 데이터 국경이동(PIPL 등) 이슈 → 실서비스 이관 전 회사 법무 검토. 크로스보더 전송이 규제 포인트.
- **레이트리밋·차단 회복:** 저빈도 + 정중한 지연이면 단일 IP 로 대개 충분. 차단 시 EIP 교체/증설. 공격적 재시도 금지.
- **관측성:** 수집 성공/실패·`--check` 상태를 로깅, 월 플래그 전환 시 알림. SQLite 는 이 규모엔 충분(폭증하면 재검토).
- **비용:** 상하이 경량 CVM 1대 + 소량 트래픽이면 월 몇천 원~만 원대(MSP 채널가로 확정). 상용 프록시(월 수만~수십만 원)보다 저렴.
- **수집 범위 현실:** 현재 환경 기준 도우인·씨트립·마펑워는 공개 수집 가능, 샤오홍슈·디엔핑은 로그인 쿠키 필요. 샤오홍슈가 대상 볼륨의 대부분이므로 쿠키 확보가 커버리지의 관건.
